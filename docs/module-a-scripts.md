# Скрипты модуля А: что делает каждый файл

В учебном решении модуль А разбит на **7 основных Python-скриптов**.

Важно: **число 7 не является требованием конкурсного задания**. Это наша структура, чтобы было проще учиться, отлаживать этапы и понимать, какой код какой критерий закрывает.

По конкурсному заданию важно другое:

- агенты должны быть автономными модулями с понятным интерфейсом;
- взаимодействие может идти через файлы, БД или API;
- после установки окружения все скрипты должны запускаться одной командой;
- итоговая система должна показывать сквозной процесс обработки данных.

Поэтому физически можно сделать и 7 файлов, и 3 файла, и один основной `module_a.py` — если все критерии выполняются.

---

## Общая схема

~~~text
01_download_tracks.py
        ↓
GPX-файлы
        ↓
02_build_dataset.py
        ↓
dataset.csv
        ↓
03_make_maps.py
        ↓
PNG-карты + map_legend.md
        ↓
05_analyze_features.py
        ↓
dataset_enriched.csv + графики + выводы
        ↓
04_load_db.py
        ↓
PostgreSQL
        ↓
06_augment_images.py
        ↓
дополнительные изображения
        ↓
07_make_report.py
        ↓
report.md
~~~

`run.sh` запускает весь процесс одной командой.

# 1. 01_download_tracks.py

## Для чего нужен

Автоматически скачивает GPX-треки по URL.

## Что получает

`training-data/tracks.json` — список маршрутов, их id, источник и URL.

## Что делает

1. читает список маршрутов;
2. фильтрует `provided` / `additional` / `all`;
3. делает HTTP-запрос;
4. скачивает GPX;
5. сохраняет файл в `work/tracks/`.

## Что создаёт

~~~text
work/tracks/
├── route_01.gpx
├── route_02.gpx
└── ...
~~~

## Какой смысл

Закрывает автоматическую загрузку исходных треков. Если сломалась только загрузка, можно чинить этот этап отдельно.

---

# 2. 02_build_dataset.py

## Для чего нужен

Это главный скрипт сбора данных. Он превращает GPX в таблицу и дополняет точки внешними данными.

## Что получает

- `work/tracks/*.gpx`;
- `training-data/tracks.json`.

## Что делает

Для каждой GPS-точки:

1. разбирает GPX;
2. получает координаты и время;
3. получает частоту шагов;
4. получает высоту;
5. получает температуру, влажность, осадки и ветер;
6. получает объекты OpenStreetMap;
7. оставляет объекты в радиусе 500 м;
8. определяет тип местности;
9. собирает строку датасета.

## Что создаёт

`work/dataset.csv`.

Одна строка — одна GPS-точка.

Главные поля:

~~~text
track_id
date
region
latitude
longitude
cadence
elevation
temperature
humidity
precipitation
wind_speed
terrain_type
nearby_objects
~~~

## Какой смысл

Это центральный этап модуля А: именно здесь разрозненные источники превращаются в один набор данных.

---

# 3. 03_make_maps.py

## Для чего нужен

Создаёт топографическую карту для каждого маршрута и рисует поверх неё трек.

## Что получает

`work/tracks/*.gpx`.

## Что делает

1. читает координаты трека;
2. переводит координаты в номера тайлов карты;
3. скачивает OpenTopoMap;
4. склеивает тайлы;
5. рисует маршрут;
6. отмечает начало/конец;
7. сохраняет PNG;
8. создаёт описание легенды карты.

## Что создаёт

~~~text
work/maps/route_01.png
work/maps/route_02.png
...
work/map_legend.md
~~~

## Какой смысл

Закрывает критерии по картам и помогает отдельно показать работу с легендой.

---

# 4. 04_load_db.py

## Для чего нужен

Записывает результаты в PostgreSQL и защищает БД от дублей.

## Что получает

В первую очередь `work/dataset_enriched.csv`, а если его ещё нет — `work/dataset.csv`.

Также использует `sql/schema.sql`.

## Что делает

1. подключается к PostgreSQL;
2. создаёт таблицы;
3. записывает маршруты;
4. записывает точки;
5. использует `ON CONFLICT ... DO UPDATE`;
6. при повторном запуске обновляет запись вместо создания копии.

## Что создаёт

Таблицы:

~~~text
tracks
route_points
~~~

## Какой смысл

Закрывает два отдельных критерия: БД без дублей и повторный запуск без дублирования.

---

# 5. 05_analyze_features.py

## Для чего нужен

Выполняет предобработку и статистический анализ датасета.

## Что получает

`work/dataset.csv`.

## Что делает

Добавляет признаки:

~~~text
month
hour
season
time_of_day
elevation_band
has_water
has_road
has_settlement
has_wetland
nearby_object_count
~~~

Также:

- считает корреляции;
- строит матрицу корреляций;
- строит гистограммы;
- выполняет Jarque–Bera;
- считает skewness и kurtosis;
- формирует словарь данных;
- пишет выводы о распределениях.

## Что создаёт

~~~text
work/dataset_enriched.csv
work/correlation.png
work/data_dictionary.md
work/conclusions.md
work/distributions/
~~~

## Какой смысл

Закрывает признаки, сезонность, описание атрибутов и проверку распределений.

---

# 6. 06_augment_images.py

## Для чего нужен

Создаёт дополнительные изображения на основе готовых карт.

## Что получает

`work/maps/*.png`.

## Что делает

Для каждой карты создаёт варианты:

- поворот;
- сдвиг;
- изменение яркости.

## Что создаёт

~~~text
work/augmented/
├── route_01_rot90.png
├── route_01_shift.png
├── route_01_bright.png
└── ...
~~~

## Какой смысл

Закрывает критерий аугментации изображений.

---

# 7. 07_make_report.py

## Для чего нужен

Собирает итоговые результаты модуля А в один отчёт.

## Что получает

Уже готовые результаты:

- `dataset_enriched.csv`;
- `maps/`;
- `augmented/`;
- `data_dictionary.md`;
- `conclusions.md`;
- `map_legend.md`.

## Что делает

1. считает маршруты и точки;
2. считает карты и аугментации;
3. вставляет пример датасета;
4. описывает источники;
5. описывает БД;
6. описывает предобработку;
7. перечисляет итоговые файлы;
8. формирует Markdown.

## Что создаёт

`work/report.md`.

## Какой смысл

Эксперт получает понятный итог, не разбирая весь код вручную.

# Вспомогательный common.py

Это **не один из семи основных этапов**.

В нём лежит общий код, который нужен нескольким скриптам:

- пути к папкам;
- чтение `tracks.json`;
- разбор GPX;
- кэш API;
- настройки PostgreSQL.

Он нужен только для того, чтобы не копировать одинаковые функции во все семь файлов.

---

# run.sh

Это тоже не этап обработки данных.

Он просто запускает скрипты в правильном порядке:

~~~bash
python src/01_download_tracks.py --source all
python src/02_build_dataset.py
python src/03_make_maps.py
python src/05_analyze_features.py
python src/04_load_db.py
python src/06_augment_images.py
python src/07_make_report.py
~~~

Запуск всего модуля:

~~~bash
bash run.sh
~~~

Это помогает выполнить требование «все скрипты запускаются одной командой».

# Обязательно ли делать именно 7 скриптов?

**Нет.**

В конкурсном задании нет требования «модуль А должен состоять из семи Python-файлов».

Требуется логическая модульность и единый запуск, а не конкретное количество файлов.

## Можно объединить всё в один файл

Например:

~~~text
module_a.py
~~~

Внутри:

~~~python
def download_tracks():
    ...

def build_dataset():
    ...

def make_maps():
    ...

def analyze_features():
    ...

def load_db():
    ...

def augment_images():
    ...

def make_report():
    ...


def main():
    download_tracks()
    build_dataset()
    make_maps()
    analyze_features()
    load_db()
    augment_images()
    make_report()


if __name__ == "__main__":
    main()
~~~

И запускать:

~~~bash
python module_a.py
~~~

Такой вариант тоже может полностью закрыть модуль А.

## Почему мы всё-таки оставили 7 файлов

Не из-за требования задания, а потому что на чемпионате это практичнее:

~~~text
сломалась загрузка
→ исправляем только 01

сломался API
→ исправляем только 02

не строится карта
→ исправляем только 03

ошибка PostgreSQL
→ исправляем только 04

ошибка статистики
→ исправляем только 05

ошибка аугментации
→ исправляем только 06

ошибка отчёта
→ исправляем только 07
~~~

То есть каждый этап можно отдельно проверить и перезапустить.

## Ещё один хороший вариант

~~~text
module_a/
├── downloader.py
├── dataset.py
├── maps.py
├── database.py
├── analysis.py
├── augmentation.py
├── report.py
└── main.py
~~~

`main.py` только связывает компоненты.

Это аккуратнее архитектурно, но для трёхчасового задания не обязательно.

# Что лучше на чемпионате

Для набора баллов я бы оставил нашу текущую схему:

**несколько простых этапов + одна команда через run.sh**.

Она удобнее для отладки и наглядно показывает эксперту, что каждый критерий реально реализован.

Главное: **количество файлов не оценивается**. Оценивается результат и воспроизводимость решения.
