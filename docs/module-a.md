# Модуль А — сбор и предварительная обработка данных

> Цель этой инструкции — не строить «идеальный production», а за 3 часа последовательно закрыть критерии оценки модуля А и получить максимум из **22 баллов**.

## Как читать эту статью

Здесь недостаточно просто копировать команды. Для каждого этапа важно понимать:

1. **что мы делаем**;
2. **зачем это нужно**;
3. **что появляется после этого действия**;
4. **как проверить результат**;
5. **какой критерий оценки этим закрывается**.

На чемпионате это помогает быстро восстанавливаться, если что-то сломалось: студент понимает не только команду, но и роль каждого шага во всём процессе.

## 1. Что требует задание

Модуль А — инвариантный. На него отводится **3 часа**.

По конкурсному заданию участник должен:

1. автоматически загрузить предоставленные треки;
2. получить топографическую карту для каждого трека и наложить маршрут на карту;
3. дополнить данные внешними источниками: погодой, рельефом и сведениями о местности;
4. сохранить треки, изображения и метаданные в базе данных;
5. для каждой точки маршрута получить окружение в радиусе 500 м;
6. сформировать итоговый набор данных;
7. определить значимые признаки и добавить признаки для всесезонности;
8. описать структуру набора данных и проверить распределения;
9. добавить новые треки и выполнить аугментацию изображений;
10. подготовить отчёт.

В опубликованном комплекте конкурсной документации конкретные исходные GPX-файлы/ссылки не приложены. Поэтому в этом репозитории есть **тренировочный набор**. Он не является официальными данными чемпионата.

## Что уже есть в учебном репозитории, а что будет на чемпионате

Это принципиально важно.

Файл вроде `src/01_download_tracks.py` **не выдаётся организаторами**. Такое имя придумали мы сами для удобства обучения.

В учебном репозитории готовые файлы лежат как **эталонное решение**, чтобы после самостоятельной попытки можно было сравнить свой код с рабочим вариантом.

На чемпионате участник получает задание, исходные данные/ссылки и подготовленную инфраструктуру. **Программу для выполнения задания он пишет сам.**

| Файл/папка | В учебном репозитории | На чемпионате |
|---|---|---|
| `training-data/tracks.json` | мы подготовили тренировочный список | организаторы дадут свои исходные данные/ссылки; формат может отличаться |
| `src/01_download_tracks.py` | готовый эталон | **пишем сами** |
| `src/02_build_dataset.py` | готовый эталон | **пишем сами** |
| `src/03_make_maps.py` | готовый эталон | **пишем сами** |
| `src/04_load_db.py` | готовый эталон | **пишем сами** |
| `src/05_analyze_features.py` | готовый эталон | **пишем сами** |
| `src/06_augment_images.py` | готовый эталон | **пишем сами** |
| `src/07_make_report.py` | готовый эталон | **пишем сами** |
| `src/common.py` | наш вспомогательный файл | не обязателен; можно создать свой |
| `sql/schema.sql` | эталон схемы БД | **пишем сами** |
| `environment.yml` | готовый пример | **создаём сами** |
| `run.sh` | готовый пример | **создаём сами** |
| `compose.yml` | только для домашней тренировки | обычно не нужен, если PostgreSQL уже подготовлен площадкой |

То есть правильная тренировка выглядит так:

~~~text
сначала читаем критерий
        ↓
понимаем, какой результат нужен
        ↓
пишем свой код
        ↓
запускаем
        ↓
проверяем результат
        ↓
только потом сравниваем с эталоном в src/
~~~

Это **не требование чемпионата**.

~~~text

        ↓
02_build_dataset.py
        ↓
03_make_maps.py
        ↓
...
~~~

На чемпионате можно назвать файлы иначе. Важно, чтобы решение выполняло требования критериев.

# Шаг 0. Подготавливаем Python-окружение

## Что такое conda и зачем она нужна

**conda** — менеджер окружений и пакетов. Она создаёт для проекта отдельную изолированную среду со своей версией Python и своими библиотеками.

Без отдельного окружения разные проекты могут требовать разные версии Python, Pandas или Scikit-learn и конфликтовать между собой. С conda наш проект живёт в своей «коробке»:

~~~text
Ubuntu
└── conda environment: professionals-ml
    ├── Python 3.11
    ├── Pandas
    ├── NumPy
    ├── Scikit-learn
    └── Matplotlib
~~~

В конкурсной документации разрешены виртуальные окружения **venv / conda**, а в инфраструктурном листе предусмотрена **Anaconda**, поэтому conda — безопасный вариант для подготовки.

> Это не отдельные баллы модуля А, но в общих критериях всех модулей отдельно оцениваются виртуальное окружение и наличие `environment.yml` / `requirements.txt`.

## Что такое environment.yml

Файл `environment.yml` описывает, какие версии Python и библиотек нужны проекту. Благодаря этому одинаковое окружение можно восстановить одной командой, а не устанавливать всё вручную.

### Как создать environment.yml самому

На чемпионате этот файл тоже нужно создать самому.

Открываем `environment.yml` и записываем:

~~~yaml
name: professionals-ml

channels:
  - defaults

dependencies:
  - python=3.11
  - pandas
  - numpy
  - scikit-learn
  - matplotlib
  - pip
  - pip:
      - psycopg2-binary
~~~

Что здесь происходит:

- `name` — имя окружения;
- `python=3.11` — фиксируем версию Python;
- `pandas` и `numpy` — работа с таблицами и числами;
- `scikit-learn` — понадобится дальше для анализа и ML;
- `matplotlib` — графики и изображения;
- `psycopg2-binary` — Python-драйвер для подключения к PostgreSQL.

Если на площадке какая-то библиотека уже установлена или доступен другой PostgreSQL-драйвер, можно адаптировать файл под фактическое окружение.

### 1. Переходим в папку модуля

~~~bash
cd module-a
~~~

`cd` означает **change directory** — сменить текущую папку. После этого относительные пути вроде `src/01_download_tracks.py` и `work/dataset.csv` будут указывать на нужные файлы.

### 2. Создаём окружение из environment.yml

~~~bash
conda env create -f environment.yml
~~~

Что происходит:

1. conda читает `environment.yml`;
2. создаёт окружение `professionals-ml`;
3. устанавливает нужную версию Python;
4. устанавливает перечисленные библиотеки.

### 3. Активируем окружение

~~~bash
conda activate professionals-ml
~~~

Создать окружение недостаточно: терминал ещё может использовать системный Python. После активации команда `python` запускает Python именно из нашего окружения.

### 4. Проверяем, что всё установилось

~~~bash
python --version
python -c "import pandas, numpy, sklearn, matplotlib; print('OK')"
~~~

Первая команда показывает версию Python. Вторая пытается импортировать основные библиотеки. Если видим `OK`, окружение готово. Если здесь ошибка, дальше идти не стоит — последующие скрипты всё равно не запустятся.

## Подготавливаем PostgreSQL

На чемпионате PostgreSQL должен быть подготовлен площадкой в Docker. Там нужно использовать выданные организаторами параметры подключения.

Для домашней тренировки в репозитории есть `compose.yml`, чтобы студенту не пришлось отдельно устанавливать и настраивать PostgreSQL.

### Что такое Docker

**Docker** — инструмент для запуска программ в изолированных контейнерах.

Контейнер можно представить как отдельную лёгкую среду, внутри которой уже есть всё необходимое конкретному приложению.

В нашем случае:

~~~text
Ubuntu
│
├── Python / conda
│
└── Docker
    └── контейнер PostgreSQL
        └── база professionals
~~~

То есть PostgreSQL не устанавливается прямо в Ubuntu. Он работает внутри Docker-контейнера.

### Зачем это нужно

Без Docker пришлось бы:

1. отдельно устанавливать PostgreSQL;
2. настраивать пользователя;
3. создавать базу;
4. следить за версией;
5. исправлять различия между компьютерами.

С Docker достаточно запустить уже подготовленное окружение. Это особенно удобно на чемпионате, где важны скорость и одинаковая инфраструктура у всех участников.

Docker прямо предусмотрен инфраструктурным листом чемпионата.

### Основные понятия Docker

**Образ (image)** — готовый шаблон приложения. Например, образ PostgreSQL содержит сам PostgreSQL и всё необходимое для его запуска.

**Контейнер (container)** — запущенный экземпляр образа.

~~~text
postgres:16
    ↓
   image
    ↓
запускаем
    ↓
container
    ↓
работающий PostgreSQL
~~~

**Volume** — отдельное хранилище данных контейнера. Он нужен потому, что сам контейнер можно удалить и создать заново, а данные PostgreSQL должны сохраняться.

**Docker Compose** — способ описать запуск одного или нескольких контейнеров в YAML-файле.

В нашем проекте это:

~~~text
compose.yml
~~~

В нём описано:

- какой образ PostgreSQL использовать;
- имя базы;
- пользователь;
- пароль;
- порт;
- volume для данных.

---

## Запускаем PostgreSQL для домашней практики

~~~bash
docker compose -f compose.yml up -d
~~~

Что означает команда:

- `docker compose` — работаем с compose-файлом;
- `-f compose.yml` — используем именно этот файл;
- `up` — создать и запустить контейнеры;
- `-d` — запустить в фоне.

После этого PostgreSQL продолжает работать, а терминал остаётся свободным.

Проверяем:

~~~bash
docker compose -f compose.yml ps
~~~

В списке сервисов `postgres` должен иметь статус `Up` / `running`.

> На чемпионате `compose.yml` может вообще не понадобиться. Если PostgreSQL уже запущен площадкой, сначала посмотрите существующие контейнеры и используйте выданные параметры подключения.

## Команды Docker, которые могут пригодиться на чемпионате

Главное правило: **сначала смотрим состояние контейнера, потом что-то перезапускаем или удаляем**.

### Посмотреть запущенные контейнеры

~~~bash
docker ps
~~~

Показывает только работающие контейнеры.

Полезные столбцы:

- `NAMES` — имя контейнера;
- `STATUS` — работает ли он;
- `PORTS` — какие порты доступны.

Если нужно понять, как называется контейнер PostgreSQL, начинать стоит именно с этой команды.

---

### Посмотреть все контейнеры, включая остановленные

~~~bash
docker ps -a
~~~

Полезно, если PostgreSQL не виден в `docker ps`.

Контейнер может существовать, но иметь статус:

~~~text
Exited
~~~

Это означает, что он остановился.

---

### Посмотреть доступные Docker-образы

~~~bash
docker images
~~~

Показывает, какие образы уже скачаны на компьютер.

Например можно увидеть:

~~~text
postgres   16
~~~

Это помогает понять, есть ли локально образ PostgreSQL.

---

### Посмотреть состояние сервисов Docker Compose

Если есть compose-файл:

~~~bash
docker compose ps
~~~

или в нашей практике:

~~~bash
docker compose -f compose.yml ps
~~~

Это удобнее, чем обычный `docker ps`, когда проект запускается через Docker Compose.

---

### Запустить контейнеры из compose-файла

~~~bash
docker compose up -d
~~~

Если compose-файл называется не стандартно:

~~~bash
docker compose -f compose.yml up -d
~~~

Создаёт недостающие контейнеры и запускает их.

---

### Остановить контейнеры из compose-файла

~~~bash
docker compose down
~~~

Контейнеры будут остановлены и удалены, но **volume с данными останется**.

После:

~~~bash
docker compose up -d
~~~

PostgreSQL сможет запуститься снова с прежними данными.

---

### Перезапустить только PostgreSQL

~~~bash
docker compose restart postgres
~~~

Полезно, если контейнер работает некорректно, но удалять его не нужно.

`postgres` здесь — имя сервиса из `compose.yml`.

---

### Посмотреть логи контейнера

Сначала узнаём имя:

~~~bash
docker ps
~~~

Потом:

~~~bash
docker logs <container>
~~~

Например:

~~~bash
docker logs module-a-postgres-1
~~~

Логи помогают понять, почему PostgreSQL не запустился:

- ошибка пароля;
- занят порт;
- повреждены данные;
- контейнер завершился с ошибкой.

---

### Смотреть логи в реальном времени

~~~bash
docker logs -f <container>
~~~

Опция `-f` означает **follow**.

Терминал будет показывать новые строки журнала по мере их появления.

Выход:

~~~text
Ctrl + C
~~~

Сам контейнер при этом не остановится.

---

### Перезапустить конкретный контейнер

~~~bash
docker restart <container>
~~~

Например:

~~~bash
docker restart module-a-postgres-1
~~~

Используем, если контейнер найден через `docker ps -a`, но работает нестабильно.

---

### Зайти внутрь контейнера

~~~bash
docker exec -it <container> bash
~~~

# Шаг 1. Загрузка треков — 2 балла

## Что такое трек и GPX

Трек — это последовательность GPS-точек маршрута. Обычно каждая точка содержит широту и долготу, а также может содержать время, высоту и дополнительные параметры.

**GPX** — XML-формат для хранения таких маршрутов. Внутри него фактически лежит последовательность точек:

~~~text
точка 1 → точка 2 → точка 3 → ...
~~~

Координаты из GPX — основа дальнейшей работы: по ним мы получим погоду, высоту, объекты вокруг и построим карту.

# Шаг 2. Формируем базовый датасет

## Что такое датасет и зачем переводить GPX в таблицу

**Датасет** — таблица, где каждая строка представляет объект наблюдения. В нашем случае одна строка — одна точка маршрута.

GPX удобен для хранения GPS-маршрутов, но Pandas, SQL и будущие ML-модели удобнее работают с таблицами. Поэтому переводим данные:

~~~text
GPX/XML → строки таблицы → CSV/PostgreSQL → анализ и ML
~~~

Для табличной обработки используем **Pandas**. Это библиотека Python для чтения, фильтрации, объединения и анализа таблиц.

GPX — это XML. Чтобы не зависеть от отдельной библиотеки, его можно разобрать стандартным `xml.etree.ElementTree`.

Из каждой точки забираем:

- широту;
- долготу;
- время;
- высоту, если она есть;
- частоту шагов, если она есть в расширении GPX.

Для учебных треков частота шагов добавлена в расширения GPX специально, потому что обычный туристический GPX часто этого поля не содержит.

На реальном чемпионате берите фактическую структуру предоставленных данных.

## Как самому разобрать GPX

Чтобы следующий скрипт мог работать с точками маршрута, сначала пишем функцию парсинга GPX.

В `src/common.py` добавляем:

~~~python
import xml.etree.ElementTree as ET
from pathlib import Path


def parse_gpx(path: Path):
    root = ET.parse(path).getroot()

    ns = {
        "g": "http://www.topografix.com/GPX/1/1"
    }

    points = []

    for index, node in enumerate(root.findall(".//g:trkpt", ns)):
        lat = float(node.attrib["lat"])
        lon = float(node.attrib["lon"])

        ele_node = node.find("g:ele", ns)
        time_node = node.find("g:time", ns)

        cadence = None

        for child in node.iter():
            if child.tag.split("}")[-1].lower() == "cadence":
                if child.text:
                    cadence = float(child.text)
                    break

        points.append(
            {
                "point_index": index,
                "latitude": lat,
                "longitude": lon,
                "elevation": (
                    float(ele_node.text)
                    if ele_node is not None
                    else None
                ),
                "timestamp": (
                    time_node.text
                    if time_node is not None
                    else None
                ),
                "cadence": cadence,
            }
        )

    return points
~~~

### Что здесь происходит

`ElementTree` читает XML.

Строка:

~~~python
root.findall(".//g:trkpt", ns)
~~~

находит все элементы `trkpt` — GPS-точки.

Из атрибутов:

~~~xml
<trkpt lat="53.4021" lon="49.9262">
~~~

берём широту и долготу.

Из вложенных элементов:

~~~xml
<ele>125</ele>
<time>2025-01-15T08:00:00Z</time>
~~~

берём высоту и время.

`point_index` создаём сами: 0, 1, 2, 3... Он пригодится для уникального ключа в БД.

### Проверяем парсер отдельно

До обращения к API полезно убедиться, что GPX вообще читается:

~~~bash

from src.common import parse_gpx

print("Точек:", len(points))
print(points[0])
PY
~~~

Если видим координаты, время, высоту и cadence — парсер работает.

Отдельной команды в самом шаге нет: этот парсер потом будет вызван из `02_build_dataset.py`.

# Шаг 3. Погода, рельеф и местность — 4 балла

## Зачем дополнять координаты внешними данными

Одних координат недостаточно, чтобы описать условия маршрута. Одна и та же точка в разные сезоны может сильно отличаться: температура, состояние местности и доступность меняются.

Поэтому к каждой GPS-точке добавляем контекст:

- **температуру** — обязательный погодный признак из критериев;
- **влажность** — дополнительный признак для будущей оценки пожароопасности;
- **осадки** — дополнительный признак для будущей оценки подтоплений;
- **скорость ветра** — дополнительный признак для будущей оценки пожароопасности;
- **высоту** — характеристику рельефа;
- **объекты вокруг** — лес, воду, дорогу, населённые пункты и т. п.;
- **тип местности** — удобный категориальный признак для дальнейшего анализа.

Температура обязательна по модулю А. Влажность, осадки и ветер мы добавляем **сверх минимального требования**, потому что в модуле Б нужно будет размечать пожароопасные и потенциально затапливаемые участки, а в модуле В — обучать модель уже на этой разметке.

В учебном решении Open-Meteo используется для погоды/высоты, а OpenStreetMap + Overpass API — для объектов вокруг точки. Это наш учебный выбор: конкурсное задание требует внешние источники, но не фиксирует конкретного поставщика.

**API (Application Programming Interface)** — программный интерфейс: наш Python-скрипт отправляет HTTP-запрос внешнему сервису и получает структурированный ответ, обычно в JSON.

**JSON** — текстовый формат данных, в котором сервис возвращает поля и значения.

**Overpass API** позволяет получить географические объекты из OpenStreetMap.

Чтобы не отправлять сотни отдельных запросов, учебный скрипт делает один запрос на область всего маршрута, а затем **локально вычисляет расстояние от каждой GPS-точки до найденных объектов** и оставляет только те, которые находятся не дальше 500 метров.

То есть требование «окружение каждой точки в радиусе 500 м» сохраняется, но внешний сервис не перегружается лишними запросами.

Здесь одновременно закрываем несколько критериев:

- внешние источники — **2 балла**;
- окружение точки 500 м — **2 балла**.

### 4. Получаем погоду на нужную дату и час

~~~python
def get_weather(lat, lon, timestamp):
    dt = datetime.fromisoformat(
        timestamp.replace("Z", "+00:00")
    )

    date = dt.date().isoformat()

    query = urlencode(
        {
            "latitude": lat,
            "longitude": lon,
            "start_date": date,
            "end_date": date,
            "hourly": (
                "temperature_2m,"
                "relative_humidity_2m,"
                "precipitation,"
                "wind_speed_10m"
            ),
            "timezone": "UTC",
        }
    )

    data = get_json(
        "https://archive-api.open-meteo.com/v1/archive?"
        + query
    )

    hourly = data["hourly"]
    wanted = dt.strftime("%Y-%m-%dT%H:00")

    index = hourly["time"].index(wanted)

    return {
        "temperature": hourly["temperature_2m"][index],
        "humidity": hourly["relative_humidity_2m"][index],
        "precipitation": hourly["precipitation"][index],
        "wind_speed": hourly["wind_speed_10m"][index],
    }
~~~

Здесь важна связка:

~~~text

        ↓
~~~

### 5. Получаем объекты вокруг точки через Overpass

Для понимания самый простой запрос выглядит так:

~~~python
def get_nearby_objects(lat, lon):
    query = f"""
[out:json][timeout:25];
(
  nwr(around:500,{lat},{lon})["natural"];
  nwr(around:500,{lat},{lon})["landuse"];
  nwr(around:500,{lat},{lon})["highway"];
  nwr(around:500,{lat},{lon})["waterway"];
  nwr(around:500,{lat},{lon})["place"];
);
out tags center;
"""

    url = (
        "https://overpass-api.de/api/interpreter?"
        + urlencode({"data": query})

    data = get_json(url)

    return data["elements"]
~~~

Ключевой фрагмент:


означает «искать вокруг точки в радиусе 500 метров».

### 6. Превращаем OSM-теги в terrain_type

~~~python
def classify_terrain(elements):
    types = []
    labels = []

    for element in elements:
        tags = element.get("tags", {})

        if tags.get("natural") == "wetland":
            types.append("wetland")

        if (
            tags.get("natural") == "wood"
            or tags.get("landuse") == "forest"
        ):
            types.append("forest")

        if (
            "waterway" in tags
            or tags.get("natural") == "water"
        ):
            types.append("water")

        if "highway" in tags:
            types.append("road")

        if "place" in tags:
            types.append("settlement")

        for key in (
            "natural",
            "landuse",
            "highway",
            "waterway",
            "place",
        ):
            if key in tags:
                labels.append(
                    f"{key}={tags[key]}"
                )

    priority = [
        "wetland",
        "forest",
        "water",
        "road",
        "settlement",
    ]

    terrain = next(
        (value for value in priority if value in types),
        "other",
    )

    return terrain, ";".join(sorted(set(labels)))
~~~

Почему есть `priority`: рядом с одной точкой могут одновременно находиться лес, дорога и вода. Нам нужен один основной `terrain_type`, а полный список сохраняем отдельно в `nearby_objects`.

~~~python
def tile_xy(lat, lon, zoom=12):
    lat = max(min(lat, 85.05112878), -85.05112878)

    n = 2 ** zoom
    x = (lon + 180.0) / 360.0 * n

    lat_rad = math.radians(lat)

    y = (
        1.0
        - math.asinh(math.tan(lat_rad)) / math.pi
    ) / 2.0 * n

    return x, y
~~~

~~~python
def download_tile(x, y, zoom=12):
~~~

# Шаг 5. PostgreSQL без дублей — 2 балла

## Зачем PostgreSQL, если уже есть dataset.csv

CSV — удобный промежуточный файл: его легко открыть и проверить глазами. Но он плохо контролирует уникальность и повторные обновления.

**PostgreSQL** — СУБД, которая умеет хранить таблицы, обеспечивать уникальность записей и обновлять существующие строки. Это напрямую соответствует требованию задания поддерживать базу актуальной и не создавать дубликаты.

В инфраструктурном листе PostgreSQL уже предусмотрен в Docker, поэтому мы не вводим лишнюю технологию.

Здесь два отдельных критерия:

- БД создана, актуальна и не содержит дублей — **1 балл**;
- повторный запуск обновляет данные без дублирования — **1 балл**.

Главный принцип — **уникальный ключ + UPSERT**.

**Уникальный ключ** запрещает появление двух одинаковых точек `track_id + point_index`.

**UPSERT** означает: если записи ещё нет — вставить её; если она уже есть — обновить. Поэтому повторный запуск обновляет температуру, высоту или окружение, но не создаёт копию той же точки.

## Как сделать БД самому

Сначала пишем `sql/schema.sql`.

Минимально нужны две таблицы:

~~~sql
CREATE TABLE IF NOT EXISTS tracks (
    track_id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    region TEXT NOT NULL,
    route_date DATE NOT NULL,
    source TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS route_points (
    track_id TEXT NOT NULL,
    point_index INTEGER NOT NULL,
    point_time TIMESTAMPTZ,
    latitude DOUBLE PRECISION NOT NULL,
    longitude DOUBLE PRECISION NOT NULL,
    cadence DOUBLE PRECISION,
    elevation DOUBLE PRECISION,
    temperature DOUBLE PRECISION,
    terrain_type TEXT,
    nearby_objects TEXT,

    PRIMARY KEY (track_id, point_index),

    FOREIGN KEY (track_id)
        REFERENCES tracks(track_id)
        ON DELETE CASCADE
);
~~~

Составной `PRIMARY KEY` и есть защита от дублей.

Теперь создаём `src/04_load_db.py`.

Подключение:

# Шаг 7. Значимые признаки и всесезонность — 3 балла

## Что такое признак

**Признак** — характеристика точки или маршрута, которую можно использовать в анализе или модели: температура, высота, частота шагов, сезон, тип местности.

## Зачем искать значимые признаки

Не все столбцы одинаково полезны. Корреляционный анализ помогает быстро увидеть, какие числовые характеристики изменяются вместе. Значение корреляции находится примерно от -1 до +1: чем ближе модуль к 1, тем сильнее линейная связь.

Критерии разрешают корреляционный анализ, SHAP или permutation importance. Для трёхчасового модуля корреляция логичнее: она быстрее и не требует отдельной сложной модели.

Не используем SHAP, если цель — быстро взять баллы.

Критерий допускает **корреляционный анализ**, поэтому используем его.

## 8.3 Статистическая проверка

Критерий требует проверить нормальность не только глазами, но и статистически. Поэтому одной гистограммы недостаточно.

**Нормальное распределение** — симметричное колоколообразное распределение. Некоторые статистические методы чувствительны к форме распределения, поэтому мы должны сделать вывод: похоже ли распределение на нормальное, есть ли скошенность и нужна ли трансформация.

В учебной реализации используется тест Jarque–Bera, который можно вычислить через NumPy без отдельной статистической библиотеки.

Минимальная функция:

~~~python
import math
import numpy as np


def jarque_bera(values):
    x = np.asarray(values, dtype=float)
    x = x[np.isfinite(x)]

    n = len(x)
    z = (x - np.mean(x)) / np.std(x)

    skew = float(np.mean(z ** 3))
    excess = float(np.mean(z ** 4) - 3)

    jb = (
        n / 6
        * (
            skew ** 2
            + excess ** 2 / 4
        )
    )

    p_value = math.exp(-jb / 2)

    return jb, p_value, skew, excess
~~~

После расчёта сохраняем не только числа, но и **словесный вывод** в `work/conclusions.md`.

Проверяем именно **непрерывные числовые признаки**: частоту шагов, высоту и погодные показатели. Для категорий вроде `season` или бинарного `has_water` проверка на нормальность не имеет смысла.

В выводах для каждого числового признака пишем:

- распределение близко/не близко к нормальному;
- есть ли выраженная скошенность;
- нужна ли трансформация.

Не оставляйте только картинку — критерий отдельно требует **вывод**.

## Сколько данных получится и хватит ли их дальше

После добавления всех учебных маршрутов набор содержит:

- **20 маршрутов**;
- **15 точек в каждом маршруте**;
- около **300 строк** в итоговом датасете;

# Шаг 10. Аугментация изображений — 3 балла

## Что такое аугментация и зачем она нужна

**Аугментация** — искусственное создание дополнительных примеров на основе уже существующих изображений. Она увеличивает обучающую выборку без поиска большого количества новых маршрутов.

Например, из одной карты можно получить варианты с допустимым поворотом, сдвигом или изменением яркости.

Важно: критерий отдельно требует **сохранить географическую достоверность**. Поэтому нельзя бездумно искажать изображение так, чтобы карта перестала соответствовать реальному маршруту; в отчёте нужно объяснить, какие преобразования применялись и почему они допустимы.

## Как написать аугментацию

Открываем `src/06_augment_images.py`.

~~~python
import matplotlib.pyplot as plt
import numpy as np
from pathlib import Path


MAPS_DIR = Path("work/maps")
AUG_DIR = Path("work/augmented")

AUG_DIR.mkdir(
    parents=True,
    exist_ok=True,
)


for path in MAPS_DIR.glob("*.png"):
    image = plt.imread(path)

    rotated = np.rot90(image)

    shifted = np.roll(
        image,
        shift=(20, 30),
        axis=(0, 1),
    )

    bright = image.copy()
    bright[..., :3] *= 1.15

    plt.imsave(
        AUG_DIR / f"{path.stem}_rot90.png",
        np.clip(rotated, 0, 1),
    )

    plt.imsave(
        AUG_DIR / f"{path.stem}_shift.png",
        np.clip(shifted, 0, 1),
    )

    plt.imsave(
        AUG_DIR / f"{path.stem}_bright.png",
        np.clip(bright, 0, 1),
    )
~~~

После написания:

~~~bash
python src/06_augment_images.py
~~~

Для скорости используем:

- поворот на 90°;
- сдвиг;
- изменение яркости.

В отчёте фиксируем:

> Аугментация используется для тренировочного изображения маршрута и не изменяет исходные географические координаты в базе данных.

## Зачем нужен run.sh

После настройки окружения и PostgreSQL можно выполнить весь учебный pipeline одной командой:

~~~bash
bash run.sh
~~~

`run.sh` — shell-скрипт, который последовательно запускает все этапы и сразу использует **все 20 учебных маршрутов**. Он удобен для финальной проверки проекта после того, как студент уже прошёл каждый шаг вручную и понимает, что происходит внутри.

Это снижает шанс забыть этап и одновременно готовит проект к общему критерию соревнования **«все скрипты запускаются одной командой после установки окружения»**.

После модуля А полученный `dataset_enriched.csv` и PostgreSQL становятся входом для **модуля Б — анализ и визуализация данных**.

## Типовые проблемы при самостоятельном прохождении

### `conda: command not found`

Anaconda/Miniconda не установлена или conda не инициализирована в текущем терминале. На чемпионате Anaconda предусмотрена инфраструктурой; дома сначала установите её и откройте новый терминал.

### Ошибка подключения к PostgreSQL / `connection refused`

Проверьте контейнер:

~~~bash
docker compose -f compose.yml ps
~~~

Если PostgreSQL не запущен:

~~~bash
docker compose -f compose.yml up -d
~~~

### Внешний API временно не отвечает

Скрипт использует кэш в `work/cache/`. Уже успешно полученные ответы не запрашиваются повторно. Если один сервис временно недоступен, можно повторно запустить только проблемный этап.

### После `--source provided` получилось больше 12 треков

Скорее всего в `work/tracks/` остались дополнительные GPX от прошлого прохождения. Для домашней тренировки сбросьте `work/` и начните заново.

### Почему `run.sh` сразу использует все 20 маршрутов

Ручное прохождение статьи специально разделяет исходные и дополнительные треки, чтобы студент понял критерий расширения набора данных. `run.sh` предназначен для финальной проверки и прогоняет уже весь учебный набор целиком.
