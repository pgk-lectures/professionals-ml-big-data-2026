# Модуль А — сбор и предварительная обработка данных

> Цель этой инструкции — не строить «идеальный production», а за 3 часа последовательно закрыть критерии оценки модуля А и получить максимум из **22 баллов**.

## 1. Что требует задание

Модуль А — инвариантный. На него отводится **3 часа**.

По конкурсному заданию участник должен:

1. автоматически загрузить предоставленные треки;
2. получить топографическую карту для каждого трека и наложить маршрут на карту;
3. дополнить данные внешними источниками: погодой, рельефом и сведениями о местности;
4. сохранить треки, изображения и метаданные в базе данных;
5. для каждой точки маршрута получить окружение в радиусе 500 м;
6. сформировать итоговый набор данных;
7. определить значимые признаки и добавить признаки для всесезонности;
8. описать структуру набора данных и проверить распределения;
9. добавить новые треки и выполнить аугментацию изображений;
10. подготовить отчёт.

В опубликованном комплекте конкурсной документации конкретные исходные GPX-файлы/ссылки не приложены. Поэтому в этом репозитории есть **тренировочный набор**. Он не является официальными данными чемпионата.

# Шаг 2. Формируем базовый датасет

GPX — это XML. Чтобы не зависеть от отдельной библиотеки, его можно разобрать стандартным xml.etree.ElementTree.

Из каждой точки забираем:

- широту;
- долготу;
- время;
- высоту, если она есть;
- частоту шагов, если она есть в расширении GPX.

Для учебных треков частота шагов добавлена в расширения GPX специально, потому что обычный туристический GPX часто этого поля не содержит.

На реальном чемпионате берите фактическую структуру предоставленных данных.

# Шаг 3. Погода, рельеф и местность — 4 балла

Здесь одновременно закрываем несколько критериев:

- внешние источники — **2 балла**;
- окружение точки 500 м — **2 балла**.

~~~bash

~~~

Для каждой точки скрипт должен получить:

1. высоту;
2. температуру на дату/время прохождения;
3. объекты OpenStreetMap в радиусе 500 м;
4. тип местности.

Минимальная итоговая строка:

| Поле | Пример |
|---|---|
| track_id | route_01 |
| date | 2025-01-15 |
| region | Самарская область |
| latitude | 53.406 |
| longitude | 49.932 |
| cadence | 103 |
| elevation | 184 |
| temperature | -8.4 |
| terrain_type | forest |
| nearby_objects | path;forest;water |

## Как определять terrain_type максимально просто

По данным OSM используем простые правила:

- natural=wood или landuse=forest → forest;
- natural=wetland → wetland;
- waterway=* или natural=water → water;
- highway=* → road;
- place=* / building=* → settlement;
- иначе → other.

При этом в отчёте отдельно пишем, что условные обозначения сверялись с легендой используемой топографической карты.

# Шаг 5. PostgreSQL без дублей — 2 балла

Здесь два отдельных критерия:

- БД создана, актуальна и не содержит дублей — **1 балл**;
- повторный запуск обновляет данные без дублирования — **1 балл**.

Главный принцип — **уникальный ключ + UPSERT**.

~~~sql
UNIQUE (track_id, point_index)
~~~

~~~sql
INSERT INTO route_points (...)
VALUES (...)
ON CONFLICT (track_id, point_index)
DO UPDATE SET
    temperature = EXCLUDED.temperature,
    elevation = EXCLUDED.elevation,
    terrain_type = EXCLUDED.terrain_type,
    nearby_objects = EXCLUDED.nearby_objects;
~~~

~~~bash
python src/04_load_db.py
python src/04_load_db.py
~~~

Количество строк после второго запуска не должно удвоиться.

## 8.3 Статистическая проверка

В учебной реализации используется простой тест Jarque–Bera, который можно вычислить через NumPy без отдельной статистической библиотеки.

В выводах для каждого числового признака пишем:

- распределение близко/не близко к нормальному;
- есть ли выраженная скошенность;
- нужна ли трансформация.

Не оставляйте только картинку — критерий отдельно требует **вывод**.
