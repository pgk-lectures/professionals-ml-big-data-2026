Файл `environment.yml` описывает, какие версии Python и библиотек нужны проекту. Благодаря этому одинаковое окружение можно восстановить одной командой, а не устанавливать всё вручную.

# Шаг 1. Загрузка треков — 2 балла

## Что такое трек и GPX

Трек — это последовательность GPS-точек маршрута. Обычно каждая точка содержит широту и долготу, а также может содержать время, высоту и дополнительные параметры.

**GPX** — XML-формат для хранения таких маршрутов. Внутри него фактически лежит последовательность точек:

~~~text
точка 1 → точка 2 → точка 3 → ...
~~~

Координаты из GPX — основа дальнейшей работы: по ним мы получим погоду, высоту, объекты вокруг и построим карту.

## Зачем нужен tracks.json

`training-data/tracks.json` имитирует список ссылок, который организаторы могут выдать участнику. Скрипт читает этот список и скачивает маршруты автоматически. Это важно: ручное скачивание через браузер не демонстрирует требуемую автоматизацию.

## Что проверяют

> Загружены все предоставленные треки.

Не нужно делать сложный загрузчик. Главное — чтобы программа получила список URL и автоматически скачала все файлы.

~~~bash
python src/01_download_tracks.py
~~~

Команда запускает Python-скрипт загрузки. Он читает URL из `tracks.json`, скачивает каждый GPX и сохраняет его в `work/tracks/`.

После выполнения:

~~~text
work/tracks/route_01.gpx
work/tracks/route_02.gpx
...
~~~

Количество скачанных файлов должно совпадать с количеством записей в tracks.json.

~~~bash
ls work/tracks/*.gpx | wc -l
~~~

Если в задании дали 6 ссылок — должно быть 6 файлов.

**Не скачивайте файлы руками.** Критерий сформулирован как автоматическая загрузка агентом.

# Шаг 2. Формируем базовый датасет

## Что такое датасет и зачем переводить GPX в таблицу

**Датасет** — таблица, где каждая строка представляет объект наблюдения. В нашем случае одна строка — одна точка маршрута.

GPX удобен для хранения GPS-маршрутов, но Pandas, SQL и будущие ML-модели удобнее работают с таблицами. Поэтому переводим данные:

~~~text
GPX/XML → строки таблицы → CSV/PostgreSQL → анализ и ML
~~~

Для табличной обработки используем **Pandas**. Это библиотека Python для чтения, фильтрации, объединения и анализа таблиц.

GPX — это XML. Чтобы не зависеть от отдельной библиотеки, его можно разобрать стандартным `xml.etree.ElementTree`.

Из каждой точки забираем:

- широту;
- долготу;
- время;
- высоту, если она есть;
- частоту шагов, если она есть в расширении GPX.

Для учебных треков частота шагов добавлена в расширения GPX специально, потому что обычный туристический GPX часто этого поля не содержит.

На реальном чемпионате берите фактическую структуру предоставленных данных.

# Шаг 3. Погода, рельеф и местность — 4 балла

## Зачем дополнять координаты внешними данными

Одних координат недостаточно, чтобы описать условия маршрута. Одна и та же точка в разные сезоны может сильно отличаться: температура, состояние местности и доступность меняются.

Поэтому к каждой GPS-точке добавляем контекст:

- **погоду** — чтобы знать температуру на момент прохождения;
- **высоту** — характеристику рельефа;
- **объекты вокруг** — лес, воду, дорогу, населённые пункты и т. п.;
- **тип местности** — удобный категориальный признак для дальнейшего анализа.

В учебном решении Open-Meteo используется для погоды/высоты, а OpenStreetMap + Overpass API — для объектов вокруг точки. Это наш учебный выбор: конкурсное задание требует внешние источники, но не фиксирует конкретного поставщика.

**Overpass API** позволяет спросить у OpenStreetMap: «какие объекты находятся в радиусе 500 метров от этой координаты?». Это и даёт нам автоматический способ заполнить `nearby_objects`.

Здесь одновременно закрываем несколько критериев:

- внешние источники — **2 балла**;
- окружение точки 500 м — **2 балла**.

~~~bash
python src/02_build_dataset.py
~~~

Для каждой точки скрипт должен получить:

1. высоту;
2. температуру на дату/время прохождения;
3. объекты OpenStreetMap в радиусе 500 м;
4. тип местности.

Минимальная итоговая строка:

| Поле | Пример |
|---|---|
| track_id | route_01 |
| date | 2025-01-15 |
| region | Самарская область |
| latitude | 53.406 |
| longitude | 49.932 |
| cadence | 103 |
| elevation | 184 |
| temperature | -8.4 |
| terrain_type | forest |
| nearby_objects | path;forest;water |

## Как определять terrain_type максимально просто

`terrain_type` нужен, чтобы превратить множество географических объектов в одну понятную категорию местности, с которой удобно работать дальше.

По данным OSM используем простые правила:

- natural=wood или landuse=forest → forest;
- natural=wetland → wetland;
- waterway=* или natural=water → water;
- highway=* → road;
- place=* / building=* → settlement;
- иначе → other.

### Важный нюанс про легенду карты

Overpass хорошо помогает получить объекты вокруг точки, но **сам по себе не закрывает критерий про интерпретацию цветов карты по легенде**.

Для полного балла по этому пункту нужно отдельно показать связь:

~~~text
цвет/условное обозначение на OpenTopoMap
        ↓
легенда OpenTopoMap
        ↓
интерпретированный тип местности
~~~

То есть в отчёте должна быть таблица используемых обозначений и несколько примеров интерпретации. Нельзя просто написать «использована легенда» без демонстрации того, как она повлияла на определение местности.

# Шаг 5. PostgreSQL без дублей — 2 балла

## Зачем PostgreSQL, если уже есть dataset.csv

CSV — удобный промежуточный файл: его легко открыть и проверить глазами. Но он плохо контролирует уникальность и повторные обновления.

**PostgreSQL** — СУБД, которая умеет хранить таблицы, обеспечивать уникальность записей и обновлять существующие строки. Это напрямую соответствует требованию задания поддерживать базу актуальной и не создавать дубликаты.

В инфраструктурном листе PostgreSQL уже предусмотрен в Docker, поэтому мы не вводим лишнюю технологию.

Здесь два отдельных критерия:

- БД создана, актуальна и не содержит дублей — **1 балл**;
- повторный запуск обновляет данные без дублирования — **1 балл**.

Главный принцип — **уникальный ключ + UPSERT**.

**Уникальный ключ** запрещает появление двух одинаковых точек `track_id + point_index`.

**UPSERT** означает: если записи ещё нет — вставить её; если она уже есть — обновить. Поэтому повторный запуск обновляет температуру, высоту или окружение, но не создаёт копию той же точки.

~~~sql
UNIQUE (track_id, point_index)
~~~

~~~sql
INSERT INTO route_points (...)
VALUES (...)
ON CONFLICT (track_id, point_index)
DO UPDATE SET
    temperature = EXCLUDED.temperature,
    elevation = EXCLUDED.elevation,
    terrain_type = EXCLUDED.terrain_type,
    nearby_objects = EXCLUDED.nearby_objects;
~~~

~~~bash
python src/04_load_db.py
python src/04_load_db.py
~~~

Количество строк после второго запуска не должно удвоиться.

Проект может запускаться и выглядеть рабочим, но один забытый столбец всё равно стоит конкретного балла. Поэтому перед сдачей не полагаемся на память, а автоматически сравниваем фактические столбцы с обязательным списком.

# Шаг 7. Значимые признаки и всесезонность — 3 балла

## Что такое признак

**Признак** — характеристика точки или маршрута, которую можно использовать в анализе или модели: температура, высота, частота шагов, сезон, тип местности.

## Зачем искать значимые признаки

Не все столбцы одинаково полезны. Корреляционный анализ помогает быстро увидеть, какие числовые характеристики изменяются вместе. Значение корреляции находится примерно от -1 до +1: чем ближе модуль к 1, тем сильнее линейная связь.

Критерии разрешают корреляционный анализ, SHAP или permutation importance. Для трёхчасового модуля корреляция логичнее: она быстрее и не требует отдельной сложной модели.

Не используем SHAP, если цель — быстро взять баллы.

Критерий допускает **корреляционный анализ**, поэтому используем его.

~~~bash
python src/05_analyze_features.py
~~~

Сохраняем:

~~~text
work/correlation.png
work/dataset_enriched.csv
~~~

## Зачем нужна всесезонность

Один и тот же маршрут зимой и летом имеет разные условия. Поэтому добавляем признаки, которые явно описывают сезон и позволяют следующим модулям учитывать время года.

Добавляем:

- `month` — номер месяца;
- `season` — winter/spring/summer/autumn;
- `temperature` — фактические погодные условия;
- высотную категорию — упрощённое описание рельефа.

~~~python
def season(month):
    if month in (12, 1, 2):
        return "winter"
    if month in (3, 4, 5):
        return "spring"
    if month in (6, 7, 8):
        return "summer"
    return "autumn"
~~~

## 8.1 Словарь данных

**Словарь данных** объясняет, что означает каждый столбец, в каких единицах он измеряется и зачем нужен. Это позволяет эксперту понять датасет без чтения Python-кода.

Создаём work/data_dictionary.md.

| Поле | Расшифровка | Единицы | Назначение |
|---|---|---|---|
| cadence | частота шагов | шаг/мин | характеристика активности |
| elevation | высота над уровнем моря | м | оценка рельефа |
| temperature | температура воздуха | °C | погодные условия |

## 8.2 Графическая проверка

Строим **гистограммы**. Они показывают, как часто встречаются разные значения признака и помогают заметить скошенность, выбросы и необычную форму распределения.

~~~text
work/distributions/cadence.png
work/distributions/elevation.png
work/distributions/temperature.png
~~~

## 8.3 Статистическая проверка

Критерий требует проверить нормальность не только глазами, но и статистически. Поэтому одной гистограммы недостаточно.

**Нормальное распределение** — симметричное колоколообразное распределение. Некоторые статистические методы чувствительны к форме распределения, поэтому мы должны сделать вывод: похоже ли распределение на нормальное, есть ли скошенность и нужна ли трансформация.

В учебной реализации используется тест Jarque–Bera, который можно вычислить через NumPy без отдельной статистической библиотеки.

В выводах для каждого числового признака пишем:

- распределение близко/не близко к нормальному;
- есть ли выраженная скошенность;
- нужна ли трансформация.

Не оставляйте только картинку — критерий отдельно требует **вывод**.

# Шаг 9. Дополнительные треки — 1 балл

## Зачем расширять датасет

Несколько исходных маршрутов дают слишком узкую выборку. Дополнительные треки добавляют другие территории и условия, а значит делают данные разнообразнее для последующей аналитики и ML.

В учебном `tracks.json` часть маршрутов помечена `source=additional`.

Это имитация пункта «добавить треки с туристических платформ».

На соревновании нужно найти хотя бы один дополнительный публичный трек, прогнать его через **тот же pipeline** и привести к той же структуре.

# Шаг 10. Аугментация изображений — 3 балла

## Что такое аугментация и зачем она нужна

**Аугментация** — искусственное создание дополнительных примеров на основе уже существующих изображений. Она увеличивает обучающую выборку без поиска большого количества новых маршрутов.

Например, из одной карты можно получить варианты с допустимым поворотом, сдвигом или изменением яркости.

Важно: критерий отдельно требует **сохранить географическую достоверность**. Поэтому нельзя бездумно искажать изображение так, чтобы карта перестала соответствовать реальному маршруту; в отчёте нужно объяснить, какие преобразования применялись и почему они допустимы.

~~~bash
python src/06_augment_images.py
~~~

Для скорости используем:

- поворот на 90°;
- сдвиг;
- изменение яркости.

В отчёте фиксируем:

> Аугментация используется для тренировочного изображения маршрута и не изменяет исходные географические координаты в базе данных.

## Зачем нужен run.sh

После настройки окружения и PostgreSQL:

~~~bash
bash run.sh
~~~

`run.sh` — shell-скрипт, который последовательно запускает все этапы. Вместо семи отдельных команд студент выполняет одну.

Это снижает шанс забыть этап и одновременно готовит проект к общему критерию соревнования **«все скрипты запускаются одной командой после установки окружения»**.
